# Twitter Feed Voice News Reader — Plan

## Context

The user wants a personal "radio" built from their own Twitter home feed: the VPS periodically turns the feed into topics, each with a **summary** and a **deep dive** (text + pre-generated audio), the Android phone plays them over its speaker / Bluetooth speaker with Next / Back / Expand controls, text is always shown alongside audio, and an **optional** ESP32 with dials/buttons can act as a physical remote over BLE. Everything must run fine on a $1/mo RackNerd VPS (~512MB–1GB RAM) and work fully without the ESP32.

User decisions (asked & answered):
- **Phone:** Android (custom APK, BLE + keep-awake are straightforward)
- **Feed access:** cookie-based calls to Twitter's internal timeline API (NOT Playwright/Chrome — too heavy for this VPS)
- **APIs:** Anthropic Claude for summaries (provider swappable to OpenAI/DeepSeek), OpenAI TTS for voice
- **Refresh:** cron twice a day, plus an on-demand refresh endpoint

## Deliberate simplifications vs. the original AI-generated prompt (explain these to the user)

1. **No Playwright/Chrome/Xvfb.** A real Chrome needs ~500MB+ RAM. Instead the server calls Twitter's internal GraphQL `HomeTimeline` endpoint directly using exported session cookies (`auth_token` + `ct0`) — same login risk, ~50MB RAM, far fewer moving parts.
2. **No WebSocket audio streaming, no server-side /skip /next /expand.** The user explicitly wants everything *prepared beforehand* and lag-free. So the server pre-generates all text + MP3s; the app downloads the whole briefing once and navigation (Next/Back/Expand) is purely local. Simpler, instant, works offline mid-commute.
3. Everything else from the prompts is kept: onboarding, interest profile, /test with mock tweets, `node test.js`, ESP32 firmware exactly as specced, standalone app mode, settings screen.

## Repo layout (monorepo, 3 components = the "3 steps")

```
README.md                 ← 3-step setup guide + testing order
server/                   ← Step 1: VPS backend (Node.js, plain JS)
app/                      ← Step 2: Android app (Expo dev build / React Native)
esp32/                    ← Step 3: Arduino firmware (optional remote)
```

## Step 1 — `server/` (Node.js backend)

Files:
- `src/twitter.js` — fetches home timeline via Twitter GraphQL `HomeTimeline` with cookies from `.env` (`TW_AUTH_TOKEN`, `TW_CT0`). Grabs ~150 tweets, normalizes to `{author, text, likes, retweets, url, ts}`. No browser.
- `src/llm.js` — provider abstraction: `complete(system, prompt)` supporting `anthropic` (default, `claude-sonnet-4-5` — note: the prompt's "claude-sonnet-4-6" doesn't exist), `openai`, `deepseek` (both OpenAI-compatible chat). Provider + model in `.env`.
- `src/topics.js` — one LLM call clusters tweets into ~8–15 topics using the user's interest profile (`data/profile.json`); per topic returns title, `autoExpand` flag (does the user care enough to auto-play the deep dive after the summary?), then per-topic LLM calls generate **summary text** (2–4 sentences) and **deep-dive text** (everything from the feed about that subject, so no need to scroll Twitter — a few paragraphs, not academic). Both are generated for *every* topic, per the user's requirement.
- `src/tts.js` — OpenAI TTS (`gpt-4o-mini-tts` or `tts-1`), text → MP3 file. Voice/model in `.env`.
- `src/build.js` — the pipeline: fetch → cluster → write texts → TTS all segments → write `data/briefings/<timestamp>/episode.json` (topics array: title, summaryText, deepDiveText, summaryAudio, deepDiveAudio, autoExpand) + MP3s → update `data/latest.json` pointer → delete briefings older than `RETENTION_DAYS` (default 7).
- `src/server.js` (Express, bearer-token auth via `API_TOKEN`):
  - `GET /playlist` — latest episode.json (text + audio URLs)
  - `GET /audio/...` — static MP3s
  - `POST /onboarding` — saves questionnaire answers to `data/profile.json`
  - `GET /status` — last build time, topic count, uptime
  - `POST /refresh` — triggers a rebuild in the background
  - `GET /test` — runs the pipeline on bundled mock tweets (no Twitter, tiny TTS cost), returns a playable mini-playlist
- `test.js` — CLI: runs full pipeline with mock tweets (or `--live` for real feed), prints texts, writes MP3s, no client needed.
- `.env.example`, `mock-tweets.json`, `README.md` with RackNerd deploy steps: `git clone`, `npm i`, fill `.env`, systemd unit for the server, cron `0 7,18 * * * node src/build.js`, and how to export the two Twitter cookies from the browser.

Cost/RAM guardrails: cap topics at ~15 and deep dives at ~1500 chars each → TTS roughly $0.30–0.60/day; Node process well under 150MB.

## Step 2 — `app/` (Expo React Native, Android, no Expo Go)

Expo + `expo-dev-client` (BLE requires a dev build), `react-native-ble-plx`, `expo-av`, `expo-keep-awake`, `expo-file-system`, AsyncStorage.

- **Data flow:** on open/refresh → `GET /playlist` → download all MP3s to app cache → build local queue. Audio files deleted from phone cache on next refresh (text lives on the VPS for a week, per user).
- **Playback model (the "analog radio" behavior):**
  - Each topic = summary segment + deep-dive segment.
  - Summary finishes → if `autoExpand`, deep dive plays; otherwise auto-advance to next topic's summary.
  - **Next** → jump to next topic's summary (skips rest of current summary/deep dive).
  - **Expand** → jump into current topic's deep dive.
  - **Back** → previous topic's deep dive (per the user's description: "goes into the previous summary('s topic) and goes into the deep dive of that topic").
  - Zero network on any of these — everything is local.
- **Main screen:** current topic title, progress bar (topic x/N + position in segment), the **full text of what's playing always visible** (scrollable), buttons: Back, Pause/Play, Next, Expand, volume slider. `useKeepAwake()` keeps the screen on so audio + BLE never die. Audio routes to phone speaker or Bluetooth speaker automatically via system routing.
- **Onboarding (first launch, chat-style, per prompt 4):** topics multi-select, favorite accounts free text, commute length slider 5–60min, depth brief/moderate/deep, never-topics multi-select → `POST /onboarding`, completion flag in AsyncStorage, "Redo setup" in settings.
- **Settings:** VPS URL + API token, BLE device name, Test Mode button (calls `/test`, plays mock audio), redo onboarding.
- **BLE (optional):** scan for the ESP32 by name, subscribe to its characteristic; incoming `"SKIP"`, `"NEXT_TOPIC"`, `"EXPAND"`, `"VOLUME_UP"/"VOLUME_DOWN"` call the exact same handlers as the UI buttons. App is fully functional if no ESP32 is found; connection state shown as a small badge.
- `app/README.md`: build instructions (`npx expo prebuild` + `npx expo run:android`, or EAS build for an installable APK).

## Step 3 — `esp32/twitter_radio_remote/twitter_radio_remote.ino`

Arduino firmware exactly per prompt 2:
- BLE peripheral (NimBLE-Arduino), service + characteristic UUIDs as constants at top, device name constant.
- Rotary encoder 1 → notify `"SKIP"`; encoder 2 → `"VOLUME_UP"`/`"VOLUME_DOWN"`; button 1 → `"EXPAND"`; button 2 → `"NEXT_TOPIC"`.
- All inputs debounced; onboard LED blinks on BLE connect; when no central connected, signals print to Serial (test mode).
- Pin assignments as constants; wiring notes in `esp32/README.md`.

## Top-level README — setup + testing order

1. VPS: clone, `.env`, `node test.js` (mock) then `node test.js --live` → confirms scrape + summarize + TTS.
2. App: build APK, Settings → set VPS URL → Test Mode → hear mock audio; then pull real playlist.
3. ESP32 (optional): flash, open Serial monitor, twist dials → see signals; then connect from app via BLE → dials control playback.

## Verification

- `cd server && npm i && node test.js` runs the full mock pipeline end-to-end (needs Anthropic + OpenAI keys in `.env`); confirm episode.json + MP3s are produced and playable.
- Start `node src/server.js`, curl `/status`, `/test`, `/playlist` with the bearer token.
- App: `npx expo run:android` isn't possible in this environment, so verify with `npx tsc --noEmit` / lint and a careful review of the playback state machine; the README's testing order covers on-device verification for the user.
- ESP32: compile-check not available here; keep firmware to well-known NimBLE patterns and document Serial test mode.
